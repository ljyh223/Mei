# 多歌手演唱角色识别系统
## 项目目标与 AI 开发任务书 V1.0

**项目性质：** 独立算法研究与软件开发项目  
**研究方向：** Music Information Retrieval（音乐信息检索）、Singer Diarization（歌手分离与角色归属）、音频深度学习  
**项目定位：** 研究原型 → 完整软件系统 → 软件著作权 → 可选学术论文  
**开发方式：** AI 辅助研发，人工评估技术路线与实验结果

---

# 一、项目背景

现有音乐播放器通常能够显示逐字歌词，但对歌曲中不同演唱者的识别能力有限。

在双人对唱、多歌手交替演唱、和声与合唱等场景中，如果没有人工标记的歌词角色信息，播放器难以自动判断每段歌词由哪位演唱者演唱。

本项目计划开发一套独立的多歌手演唱角色识别系统，通过音频分析、深度学习和歌词时间轴对齐，自动识别歌曲中不同歌手的演唱区间，并生成可供播放器使用的角色标注结果。

项目未来可以集成到 Android 音乐播放器 Mei，但核心算法和软件系统必须具备独立运行能力。

# 二、核心目标

## 2.1 主要目标

实现一套能够处理未知歌曲的自动演唱角色识别系统。

输入：

- 歌曲音频文件。
- 可选的同步歌词及时间戳（LRC、QRC、YRC 等）。
- 可选的歌手数量或其他辅助信息。

输出：

- 估计歌曲中的演唱者数量。
- 识别不同演唱者的演唱时间区间。
- 识别歌手之间的切换。
- 检测多人同时演唱的片段。
- 将演唱角色映射到对应的歌词行或歌词片段。
- 输出结构化、可供第三方软件调用的数据。

系统首先解决歌曲内部的匿名歌手归属问题，例如 Singer 1、Singer 2，而不是依赖预先录入真实歌手姓名。

## 2.2 能力分级

### Level 1：基础角色识别

- 区分单人独唱与多人演唱歌曲。
- 识别双人交替演唱。
- 对不同演唱区间分配一致的匿名歌手 ID。
- 将识别结果关联到已有歌词时间轴。

### Level 2：复杂演唱场景

- 处理不同歌手音域重叠的情况。
- 支持同性别、相似音色歌手的区分。
- 识别短句切换、连续交替演唱。
- 检测同时演唱、合唱与背景和声。
- 支持不确定结果及低置信度标注。

### Level 3：高级识别与优化

- 支持三人及以上歌手。
- 提高复杂混音中的角色识别准确率。
- 研究使用歌手特征表示、时序建模和多标签预测。
- 研究跨歌曲歌手表征的稳定性。
- 优化推理耗时、内存占用与模型体积。

以上是分阶段研究目标，不要求第一版本全部实现。

# 三、技术研究方向

本项目不局限于传统基频 F0、MFCC 或简单音高阈值判断。

允许并鼓励研究现代机器学习和深度学习技术，包括但不限于：

1. Vocal Separation：人声与伴奏分离。
2. Singing Voice Activity Detection：演唱活动检测。
3. Speaker/Singer Embedding：声音身份特征提取。
4. Clustering：基于声纹特征的歌手聚类。
5. Temporal Modeling：考虑时间连续性的角色预测。
6. Overlap Detection：多人同时演唱检测。
7. Lyric Alignment：音频与歌词时间轴对齐。
8. Fine-tuning：在必要时对预训练模型进行微调。

需要特别注意：

**人声与伴奏分离，不等于不同歌手之间的分离。**

不能假设传统说话人识别模型能够直接适用于歌唱场景，也不能假设音高、性别或音色相似程度能够唯一确定歌手身份。

## 3.1 算法路线要求

采用实验驱动的技术路线。

首先调研相关开源项目、论文、预训练模型和公开数据集，识别可复用的成熟技术。

随后建立至少一种可复现的基线方法，并尝试改进。

建议比较：

- 传统声学特征与聚类方法。
- 预训练说话人或歌手嵌入模型。
- 多特征融合方法。
- 结合歌词时间轴的时序约束方法。
- 必要时使用微调或专门训练的模型。

最终方案由实验结果决定，而不是预先指定某个模型。

# 四、数据集建设

目前项目正在准备实验数据集。

数据集是项目的重要研究资产，需要建立规范的数据格式、标注工具及版本管理方案。

## 4.1 数据类型

数据集应尽量包含：

- 单人独唱歌曲。
- 男女对唱歌曲。
- 同性别双人对唱歌曲。
- 三人及以上多人演唱歌曲。
- 同时合唱片段。
- 背景和声片段。
- 短时间交替演唱片段。
- 音色或音域接近的歌手。

## 4.2 标注要求

至少支持以下信息：

- 歌曲唯一 ID。
- 音频文件或合法数据引用。
- 歌词及时间戳。
- 匿名歌手 ID。
- 演唱片段开始和结束时间。
- 同一时间段内的多个活跃歌手。
- 无法确定的歌手片段。
- 标注版本及必要的质量信息。

角色标注必须支持多标签。

不能假设任意时间点只能存在一位演唱者。

歌词行级别标注可以作为第一阶段，但数据格式应允许未来扩展到更精细的时间段标注。

## 4.3 数据处理

需要建立可复现的数据处理流水线：

- 音频加载与格式转换。
- 重采样与时长检查。
- 可选的人声分离。
- 歌词解析和时间轴标准化。
- 特征提取。
- 标签读取与校验。
- 训练、验证和测试集划分。

必须防止同一歌曲的片段同时进入训练集和测试集而造成数据泄漏。

若研究未知歌手的泛化能力，还需设置歌手不重叠的独立测试方案。

保留数据来源、授权范围及处理记录。未经授权，不公开分发商业歌曲音频或完整歌词数据。

# 五、软件系统设计

项目应采用模块化架构，核心算法独立于具体播放器。

建议划分为以下模块：

### 1. Dataset

数据集管理、标注读取、格式转换及数据质量检查。

### 2. Audio Processing

音频预处理、人声活动分析及可选声源分离。

### 3. Feature Extraction

声学特征、预训练声纹表征及特征融合。

### 4. Diarization Engine

演唱角色聚类、时序预测、角色归属和重叠演唱检测。

### 5. Lyric Attribution

把角色识别结果映射到歌词时间轴，生成歌词角色标签。

### 6. Evaluation

自动化评测、基线对比、结果统计、错误案例分析。

### 7. Application / API

提供独立的推理接口、命令行工具和结果展示能力。

首选 Python 作为算法研究及训练环境。模型部署框架根据实际实验结果选择。

暂不要求直接部署到 Android 端，但架构上应允许未来使用 ONNX Runtime、服务端推理或其他合理方式接入 Mei。

# 六、结果输出

设计稳定、可扩展的数据接口。

至少提供：

- 歌曲 ID。
- 识别出的歌手 ID 集合。
- 歌手演唱时间片段。
- 允许多个歌手同时活跃的角色列表。
- 歌词对应的角色信息。
- 置信度或不确定性信息（模型具备可靠估计能力时）。
- 模型版本与处理配置。

输出结果必须是机器可读的结构化格式，例如 JSON。

未知、无演唱或无法可靠判断的片段，应有明确的数据表示，不允许强行分配歌手身份。

# 七、实验与评价

项目不能只以“可以运行”为完成标准。

必须通过可量化实验评估系统性能。

研究阶段应至少考虑：

- 歌手分离错误率（DER，明确是否考虑重叠）。
- 时间片段或帧级识别指标。
- 歌词行角色识别准确率。
- 重叠演唱检测 Precision、Recall、F1。
- 不同歌曲类型的识别效果。
- 推理速度、计算资源和内存占用。

针对匿名歌手 ID，评测时应处理预测标签与真实标签之间的排列对应关系。

至少比较一种基线方案与改进方案。

当样本量允许时，开展消融实验，分析不同模块的实际贡献。

不得编造实验结果，不得在缺少数据的情况下宣称算法优于现有研究。

第一阶段不设定未经实验验证的准确率目标，先取得可靠基线，再制定改进指标。

# 八、开发阶段与验收目标

## Phase 0：现状审计与研究调研

任务：

- 阅读现有项目代码及目录结构。
- 盘点已有音频、歌词及标注数据。
- 确认现有算法和实验结果。
- 查阅相关研究及开源实现。
- 识别技术难点和可复用组件。
- 制定后续开发路线。

交付：

- 项目现状分析。
- 技术路线对比。
- 数据集现状报告。
- 第一阶段实施计划。

## Phase 1：可运行基线系统

任务：

- 规范数据格式。
- 建立音频处理流水线。
- 实现基础歌手特征提取与聚类。
- 完成双人交替演唱场景识别。
- 建立基础评测工具。

交付：

- 可复现的基线代码。
- 测试样例与评测报告。
- 可导出的角色识别结果。

## Phase 2：改进识别算法

任务：

- 研究更适合歌唱场景的特征表示。
- 引入或微调适当的预训练模型。
- 实现更可靠的歌手角色归属。
- 增加重叠演唱检测。
- 对复杂歌曲开展对照实验。

交付：

- 改进后的识别引擎。
- 模型或配置管理机制。
- 多组对照实验结果。
- 典型错误案例分析。

## Phase 3：完整软件系统

任务：

- 建立统一推理接口。
- 支持批量歌曲处理。
- 支持结果可视化与人工修正。
- 支持歌词角色标注导出。
- 完善配置、日志和异常处理。
- 编写安装、使用与技术说明文档。

交付：

- 独立可运行的软件。
- 完整源代码与使用文档。
- 自动化测试。
- 软件 V1.0 发布版本。

## Phase 4：成果整理（可选）

根据项目实际成熟度：

- 整理软件著作权申请所需材料。
- 准备科研实验报告。
- 评估是否具备论文发表价值。
- 研究与 Mei 的集成方案。
- 决定是否公开部分代码或数据集。

论文发表不是当前阶段的强制交付要求。

# 九、AI Agent 开发原则

## 9.1 充分利用现有成果

项目已经存在一定的研究代码和数据整理工作。

AI 在修改前必须先检查已有结构，不允许在不了解现状的情况下重新创建重复项目或推翻已有实现。

优先复用有效代码，识别技术债务，并有依据地实施重构。

## 9.2 研究质量优先

不能为了快速交付而堆砌未经验证的算法。

优先采用：

- 可复现的实现。
- 有明确来源的模型。
- 清晰的模块边界。
- 可量化的评价指标。
- 能够进行对照实验的架构。

允许探索复杂技术，但每个复杂方案都需要证明其价值。

## 9.3 区分实现与验证

AI 可以负责代码实现、调研、实验设计和测试自动化。

但不能将代码执行成功等同于算法有效。

关键技术结论必须由真实实验数据支持。

## 9.4 保留研究记录

重大算法选择应记录：

- 研究问题。
- 实验假设。
- 实施方案。
- 模型与数据版本。
- 实验结果。
- 失败原因。
- 后续改进方向。

便于未来整理科研报告或论文。

## 9.5 工程规范

- 保持代码模块化。
- 提供明确的依赖管理。
- 保存可复现的实验配置。
- 为核心模块提供测试。
- 避免硬编码本地路径、密钥与私有接口。
- 不随意删除原始数据。
- 不擅自大规模修改项目结构。
- 重要节点使用 Git 提交。
- 保证现有可运行功能不被无故破坏。

# 十、最终目标与成功标准

本项目的最终目标不是简单完成一个软件著作权登记，而是开发一套具有实际价值、可以独立运行并持续演进的多歌手演唱角色识别系统。

项目成功应满足以下基本标准：

1. 能够处理未针对其单独编写规则的歌曲。
2. 能够输出一致的匿名演唱者标签及对应时间区间。
3. 能够与同步歌词进行角色关联。
4. 对常见对唱场景具有经过测试验证的识别能力。
5. 有可靠的实验数据、基线对比和明确的局限性说明。
6. 形成完整、可维护、可运行的软件系统。
7. 核心算法能够独立使用，并具备未来集成到 Android 播放器的可能性。

高级功能可根据研究结果逐步扩展，不以一次性完成所有难题为目标。
